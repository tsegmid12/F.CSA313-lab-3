## 1. Лабораторийн зорилго

Энэхүү лабораторийн зорилго нь программ хангамжийн чанарын шаардлагыг чанарын сценарио хэлбэрээр тодорхойлж, тэдгээрийг Service Level Objective (SLO) болгон томьёолж, Grafana k6 ашиглан автоматаар шалгах явдал юм.

Лабораторийн хүрээнд Express ашиглан локал API сервер үүсгэж, Performance, Reliability, Availability гэсэн гурван үндсэн чанарын сценарио боловсруулсан. Мөн `/report` endpoint-д зориулж дөрөв дэх нэмэлт performance threshold оруулсан.

Туршилтыг зөвхөн өөрийн локал машин дээр ажиллуулсан.

1. Тойм (Overview)
2. Системийн төлөв (System state)
3. Орчны төлөв (Environment state)
4. Гадаад өдөөлт (External stimulus)
5. Шаардлагатай хариу (Required response)
6. Хэмжүүр (Measure)

## 5. SLO хүснэгт

SLO (Service Level Objective) нь системийн үйлчилгээний чанарт тавьсан хэмжигдэхүйц зорилт юм.

| Сценарио | Endpoint / SLI | SLO босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency p95 | < 200 мс | 20 VU, 1 минут |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 минут |
| Availability | Амжилттай хүсэлтийн хувь | ≥ 90% | 2 минут, 10 секундийн зогсолт |
| Нэмэлт Performance | `/report` latency p95 | < 450 мс | 20 VU; baseline 1 минут, chaos/fail 2 минут |

### 5.1 Босго сонгосон үндэслэл

- `/cart/add` endpoint нь хэрэглэгчийн шууд үйлдэл учраас хариу хугацааг 200 мс-ээс бага байхаар сонгосон.
- `/pay` endpoint-д серверийн кодоор ойролцоогоор 5%-ийн алдаа зориудаар үүсгэдэг тул бодитой зөвшөөрөгдөх алдааны босгыг 8% гэж сонгосон.
- Availability-ийн 90%-ийн босго нь 2 минутын туршилтын хугацаанд үйлчилгээний амжилтын түвшинг хэмжих зорилготой.
- `/report` endpoint нь 200–400 мс санамсаргүй сааталтай тул бодит хариу хугацаанд үндэслэн 450 мс-ийн p95 босго сонгосон.

### 5.2 Availability Error Budget тооцоо

Availability SLO = 90%

Туршилтын хугацаа = 2 минут = 120 секунд

Зөвшөөрөгдөх зогсолтын хугацаа:

`Error Budget = 120 × (1 - 0.90)`

`Error Budget = 12 секунд`

Иймээс 2 минутын туршилтын хугацаанд систем хамгийн ихдээ 12 секунд хүртэлх зогсолттой байж болно.

Энэ нь хугацаагаар тооцсон error budget юм.

Харин хүсэлтээр тооцох error budget нь нийт хүсэлтийн 10% байна. Сервер зогссон үед хүсэлтүүд шууд амжилтгүй болж, хэвийн ажиллагааны үеийнхээс өөр хэмжээний алдаа үүсгэж болох тул хугацааны болон хүсэлтийн error budget ижил гарах албагүй.

### 5.3 Reliability Error Budget

Reliability SLO нь `/pay` endpoint-ийн error rate-ийг 8%-аас бага байлгах зорилготой.
Chaos туршилтаар `/pay` endpoint 1879 хүсэлт хүлээн авч, 267 хүсэлт амжилтгүй болсон.

`Error Budget = 1879 × 0.08 = 150.32 хүсэлт`

Бодит амжилтгүй `/pay` хүсэлт 267 байсан нь зөвшөөрөгдөх 150.32 хүсэлтээс их тул
reliability error budget хэтэрсэн. Энэ нь chaos туршилтын `/pay` error rate 14.20%
болж, `rate<0.08` threshold FAIL болсонтой нийцнэ.

### 5.4 Performance Error Budget

Performance-ийн error budget нь latency-ийн p95 босгоос давсан хүсэлтийн эзлэх хувь
юм. Энэ туршилтад `/cart/add` болон `/report` endpoint-ийн p95 утгыг тус тусын
SLO босготой харьцуулсан. PASS болон chaos үр дүнд хоёр endpoint-ийн p95 босго
хангагдсан, харин зориудын FAIL тестэд `/report`-ийн `p(95)<100` босго зөрчигдсөн.

## 6. k6 Threshold тохиргоо

`SLO`-уудыг `slo-test.js` файлд дараах threshold-уудаар хэрэгжүүлсэн.

| Metric | Threshold | Зорилго |
|---|---|---|
| `http_req_duration{name:cart}` | `p(95)<200` | Сагсны хариу хугацаа |
| `http_req_failed{name:pay}` | `rate<0.08` | Төлбөрийн алдааны хувь |
| `checks` | `rate>0.90` | Амжилттай шалгалтын хувь |
| `http_req_duration{name:report}` | `p(95)<450` | Тайлангийн хариу хугацаа |

Endpoint бүрийг `name` tag ашиглан ялгасан. Ингэснээр тухайн endpoint-ийн хэмжүүрт тусад нь threshold тавих боломжтой болсон.

**Тайлбар:** k6-ийн `checks` нь хугацааны хувь биш, нийт хийгдсэн check-үүдийн амжилтын хувь юм. Энэхүү лабораторид endpoint бүрийн HTTP 200 хариуг check болгон ашигласан.

Дэлгэрэнгүй гаралт: `results/pass.txt`

### 7.2 Chaos test — FAIL

Туршилтыг 2 минутын хугацаатай эхлүүлж, ажиллаж байх үед серверийг Ctrl+C ашиглан зогсоосон. Ойролцоогоор 10 секунд хүлээсний дараа `node server.js` командаар серверийг дахин асаасан.

Энэ туршилтын бодит тохиргоо 20 VU байсан.

Үр дүн:

| Үзүүлэлт | Бодит үр дүн | Шаардлага | Үнэлгээ |
|---|---:|---:|---|
| Checks success rate | 89.37% | > 90% | FAIL |
| `/cart/add` p95 | 2.65 мс | < 200 мс | PASS |
| `/report` p95 | 398.48 мс | < 450 мс | PASS |
| `/pay` error rate | 14.20% | < 8% | FAIL |

Нийт хүсэлт: 5637

Амжилттай хүсэлт: 5038

Амжилтгүй хүсэлт: 599

Хүсэлтээр тооцсон бодит availability:

`Availability = (Амжилттай хүсэлт / Нийт хүсэлт) × 100`

`Availability = (5038 / 5637) × 100`

`Availability ≈ 89.37%`

Хүсэлтээр тооцсон error budget:

`5637 × 10% = 563.7 хүсэлт`

Бодит амжилтгүй хүсэлт 599 байсан тул зөвшөөрөгдөх 10%-ийн хүсэлтийн error budget-ийг давсан.

**Тайлбар:** Сервер зогссон үед хүсэлтүүд connection refused зэрэг алдаагаар хурдан буцдаг. Харин сервер хэвийн үед `/report` хүсэлт 200–400 мс хүлээдэг. Иймээс 10 секундийн зогсолт нь зөвхөн 10 секундийн хугацааны алдагдал биш, харин тухайн хугацаанд үүссэн олон хүсэлтийн алдагдал болдог. Энэ нь 12 секундийн хугацааны error budget болон хүсэлтээр тооцсон error budget яагаад өөр үр дүнтэй байж болохыг харуулж байна.

`/pay`-ийн reliability threshold мөн FAIL болсон. Учир нь сервер зогссон үед `/pay` хүсэлтүүд ч амжилтгүй болж, нэг серверийн доголдол availability болон reliability хоёр SLI-д зэрэг нөлөөлсөн.

Availability нь бүх endpoint-ийн нийт амжилттай хүсэлтийн хувийг хэмждэг бол reliability нь зөвхөн `/pay` endpoint-ийн алдааны хувийг хэмждэг.

Дэлгэрэнгүй гаралт: `results/chaos.txt`

## 9. Дүгнэлт

1. Энэхүү лабораторийн ажлаар чанарын шаардлагыг сценарио, SLO болон k6 threshold болгон хувиргах үйл явцыг хэрэгжүүллээ.
2. Performance сценариогоор `/cart/add` endpoint-ийн p95 хариу хугацаа 2.22мс гарч, 200 мс-ийн шаардлагыг хангасан.
3. Reliability сценариогоор `/pay` endpoint-ийн алдааны хувь 6.06% гарч, 8%-ийн босгоос бага байсан.
4. Baseline тестийн бүх threshold PASS болсон нь сервер хэвийн нөхцөлд тогтоосон SLO-г хангаж байгааг харуулсан.
5. Chaos тестийн үеэр серверийг ойролцоогоор 10 секунд зогсооход checks-ийн амжилтын хувь 89.37% болж, availability threshold FAIL болсон.
6. Chaos тестээр `/pay` endpoint-ийн алдааны хувь 14.20% болж, reliability threshold мөн FAIL болсон.
7. Хугацаагаар тооцсон 12 секундийн error budget болон хүсэлтээр тооцсон error budget нь ачаалал, хүсэлтийн хурд, серверийн хариу үйлдлээс шалтгаалан өөр үр дүнтэй байж болохыг ойлголоо.
8. Fail тестээр `/report` endpoint-ийн threshold-ийг 100 мс болгож өөрчлөхөд k6 бодит p95 болох 398.04 мс-ийг илрүүлж, тестийг FAIL болгосон.
